# Claude Code プロンプト集

コピーしてそのまま貼れる形にしてあります。**リポジトリのルートで Claude Code を起動**
してください（`CLAUDE.md` が自動で読まれます）。

---

## 0. 使い方の3原則

1. **プロンプトを長く書かない。** ルールは `CLAUDE.md`、実験の中身は `specs/` に書いてあります。
   毎回説明し直すのは無駄で、しかもブレます。**「仕様書を読んで実装して」で足ります。**
2. **仕様書を先に書く。** 仕様が無い実験は実装させない。仕様を書く時間は第5章の執筆時間の前借りです。
3. **差分を必ず自分で読んでから commit する。** 読まずに通したコードは、口頭試問で説明できません。

### セッションの区切り方

実験1つ＝1セッションにして、終わったら `/clear` してください。
前の実験の文脈が残っていると、関係ない部分を勝手に触られることがあります。

## 1. 初回セットアップ

### 1-1. GitHub にリポジトリを作って push する

```
このリポジトリを GitHub のプライベートリポジトリとして作成して push してください。
リポジトリ名は conformal-thesis。gh コマンドが使えるならそれを使ってください。
push する前に、.gitignore で除外すべきものが漏れていないか確認してください。
特に __pycache__、.pytest_cache、*.egg-info、TeX の中間生成物です。
```

> **公開/非公開は先生の指示に従ってください。** 迷ったらプライベートにしておけば安全です。

### 1-2. 環境を作って動作確認する

```
pip install -e ".[dev]" を実行し、make test と make e1 と make e1b が通ることを確認してください。
エラーが出たら原因を説明してから直してください。
```

## 2. 実験を実装する

### 2-1. 汎用テンプレート（これが基本形）

```
specs/E<番号>_<名前>.md を読んで、experiments/e<番号>_<名前>.py を実装してください。

守ること:
- CLAUDE.md の「絶対に守ること」に従う
- 仕様書の「検証（この実験が正しく走ったと判断する基準）」を、
  実行後に自動で判定して結果を表示する
- 実装したら実行し、判定が通ることを確認する
- 通らなかった場合、実装のバグか実験設定の問題かを切り分けて説明する

まだ commit はしないでください。差分を私が読みます。
```

### 2-2. E2（下敷きモデルへの非依存性）

```
specs/E2_model_agnostic.md を読んで experiments/e2_model_agnostic.py を実装してください。
CLAUDE.md の規約に従うこと。

実装後に実行し、仕様書の検証基準（被覆率が全モデルでほぼ同一、
平均区間幅がMSEと単調に対応、定数予測器でも被覆する）を判定して表示してください。

図はまだ作らなくて結構です。csv まで出してください。
```

### 2-3. E3（条件付き被覆の破綻）★見せ場

```
specs/E3_conditional_coverage.md を読んで実装してください。以下の順で進めてください。

1. まず src/conformal/ に足りない部品を追加する
   - 正規化残差スコアの sigma(x) 推定（残差の絶対値を別に回帰する）
   - CQR 用の分位点回帰のラッパ（sklearn の GradientBoostingRegressor の
     loss="quantile" を使う）
   部品ごとに tests/ に検証テストを追加すること。
   特に CQR は tests/test_cqr_score.py の手計算例が通ることを確認する。

2. experiments/e3_conditional.py を実装して実行する

3. 仕様書の検証基準を判定して表示する
   （3手法とも周辺被覆は満たす / 絶対残差では層別被覆が割れる /
     正規化残差とCQRでばらつきが縮む / CQRの幅が X1 に応じて広がる）

1が終わった時点で一度止まって、私に確認させてください。
```

### 2-4. 図を作る

```
experiments/make_figures.py に E3 の図を追加してください。仕様書の「図」の節に従うこと。

1枚目: 横軸 X1、縦軸 Y の帯グラフ。絶対残差版とCQR版を並べ、
       予測区間の上下限を帯で描いて実データ点を重ねる
2枚目: X1 の5分位ごとの層別被覆率の棒グラフ。名目値に水平線

既存の作図の作法（色、フォント、pdf と png の両方を出す、csv からしか読まない）を
踏襲してください。実験は回し直さないこと。
```

### 2-5. 新しい実験の仕様書を書かせたいとき

**仕様は自分で書くのが原則ですが、たたき台が欲しいときは：**

```
specs/TEMPLATE.md の形式で、E4（交換可能性が破れる場合）の仕様書のたたき台を
書いてください。docs/研究計画.md の E4 の記述を出発点にしてください。

ただし「検証（この実験が正しく走ったと判断する基準）」の節は空欄にしておいてください。
そこは私が自分で決めます。
```

> **判定基準だけは自分で書いてください。** 実装とテストの両方を Claude に決めさせると、
> 同じ誤解が両方に入ってテストが通ってしまいます。ここが生成AI利用の最大の落とし穴です。

## 3. 論文を書く（TeX）

### 3-1. 章の下書き

```
thesis/R08_<Name>.tex の「準備」の章を書いてください。
各サブセクションの TODO コメントに書いてある内容に沿ってください。

条件:
- 日本語。です・ます調ではなく、である調
- 定義・補題・定理は、プリアンブルで定義済みの環境を使う
- 証明は書かず、定義と記法の整理に徹する（証明は第3章）
- 参考文献は refs.bib のキーで \cite する
- 私が後で書き換える前提で、断定しすぎないこと

書いたら、どこが薄いか・何を私が足すべきかを最後に指摘してください。
```

### 3-2. 実験結果を本文に流し込む

```
results/e1_summary.csv と figures/fig_e1_*.pdf を読んで、
thesis/R08_<Name>.tex の「E1：有限標本被覆保証の検証」の節を書いてください。

- 表は booktabs で組む。数値は csv からそのまま取ること（丸めは小数第4位）
- 図は \includegraphics で参照する
- 「何が言えたか」を最後の段落に書く

数値を創作しないでください。csv に無い値は書かないこと。
```

> **これは強く言っておいてください。** 数値の捏造は最も危険な失敗です。

### 3-3. コンパイルを通す

```
thesis/ で platex → pbibtex → platex → platex → dvipdfmx を実行し、
.log から undefined reference と warning を全部消してください。

黒沢研究室の提出要件で、undefined references が残っているもの、
pbibtex で warning が出ているものは受理されません。
docs/提出要件と締切.md の第4節を参照してください。
```

### 3-4. 付録A（数式と実装の対応表）

```
src/conformal/ の各関数の docstring に書いてある式番号を集めて、
thesis/ の付録A用に「数式と実装の対応表」を作ってください。
列は「式番号 / 数式の意味 / ファイル / 関数名」。

対応が取れていない関数、docstring に式番号が無い関数があれば指摘してください。
```

## 4. 自分の理解を守るためのプロンプト

**ここが一番大事です。** 実装を任せる以上、理解は別に確保しないといけません。

### 4-1. 口頭試問の予行演習

```
src/conformal/split.py と thesis/ の第3章を読んだうえで、
卒論の口頭試問で聞かれそうな質問を10個作って、1問ずつ私に質問してください。

私が答えたら、正しいか、足りない点は何かを指摘してください。
答えられなかった場合だけ解説してください。先に答えを言わないでください。
```

### 4-2. バグ発見の訓練

```
src/conformal/split.py に、微妙なバグを1箇所だけ入れたバージョンを
/tmp/split_buggy.py として作ってください。どこを変えたかは教えないでください。

バグは、実行してもエラーにならず、被覆率がわずかにずれる種類のものにしてください。
私が探します。
```

### 4-3. 実装を説明させる

```
src/conformal/split.py の conformal_quantile 関数について、
1行ずつ、なぜその行が必要なのかを説明してください。
特に ceil((n+1)*(1-alpha)) の (n+1) と、-1 のインデックス調整について、
理論のどこから来ているのかを説明してください。
```

### 4-4. 中核だけ自分で書き直す

```
src/conformal/split.py の conformal_quantile と conformal_pvalue を
一度削除してください。私が自分で書き直します。
tests/ はそのままにしておいてください。

書き直したら、テストが通るか確認してもらいます。
```

> **これは必ず一度やってください。** 全体の1%の労力で、口頭試問のリスクの90%が消えます。

## 5. 提出物を整える

### 5-1. Readme.txt を最新化する

```
submission/Readme_template.txt を、現在のリポジトリの中身に合わせて更新してください。
- 提出ファイル一覧を実際の src/ experiments/ results/ figures/ から作り直す
- 実行手順に、追加した実験のコマンドを足す
- 図表と本文の対応表を、thesis/ の \includegraphics と \label から作る

黒沢研究室の提出要件（docs/提出要件と締切.md の第5節）を満たしているか
最後にチェックして報告してください。
```

### 5-2. コメントの点検

```
src/ と experiments/ の全ファイルについて、提出要件を満たしているか点検してください。

- コメントが十分か（他人が読んで理解できるか）
- 卒論のどの章・どの実験に対応するかが冒頭に書かれているか
- 変数名が x や tmp のままなど、意味の分からないものが残っていないか

問題がある箇所を一覧にしてください。修正はそのあと指示します。
```

### 5-3. 提出前の総点検

```
submission/CHECKLIST.md を上から順に、リポジトリの実際の状態と突き合わせて、
機械的に確認できる項目だけ判定してください。
判定できない項目（先生に報告したか等）は「要手動確認」と出してください。
```

## 6. Git / GitHub の運用

### 6-1. コミットの型

```
今の変更を commit してください。

コミットメッセージは日本語で、1行目に何をしたか、
空行のあとに「なぜそうしたか」と「検証したこと」を書いてください。
実験を追加した場合は、判定結果の要約も入れてください。
```

### 6-2. 章や実験ごとにブランチを切る

```
E3 の実装用に feature/e3-conditional ブランチを切ってください。
作業が終わったら main にマージします。
```

> 一人プロジェクトなので main 直接でも困りませんが、**実験ごとにブランチを切ると
> 「動いていた状態」に戻れます。** 締切前に効きます。

### 6-3. 週末の定期チェック

```
以下を実行して、リポジトリが健全か報告してください。
- make test
- make e1 と make e1b を実行し、results/ の csv が前回と一致するか（再現性の確認）
- git status がクリーンか
- specs/ にあるのに experiments/ に実装が無いもの、逆に実装があるのに仕様書が無いもの

再現性が壊れていたら、原因を特定してください。
```

## 7. うまくいかないときの言い方

| 状況 | 言い方 |
|---|---|
| 実装が複雑すぎる | `この実装は私には読めません。もっと素直に書き直してください。速度より読みやすさを優先してください。` |
| 勝手に別の場所を触られた | `指示していないファイルを変更しないでください。変更したファイルを一覧にして、意図を説明してください。` |
| テストを実装に合わせて書かれた | `テストを実装に合わせて修正しないでください。テストは理論から書くものです。実装の方が間違っている可能性を検討してください。` |
| 結果が理論と合わない | `理論と合いません。実装のバグなのか、推定の分散なのかを切り分けてください。specs/E1b_detection_levels.md に切り分けの方法があります。` |
| 数値を創作された疑い | `その数値の出典を示してください。results/ のどの csv のどの行ですか。` |

## 8. やらせてはいけないこと

- **検証テストの判定基準を Claude に決めさせる**（実装と同じ誤解が入る）
- **論文の考察・結論を書かせる**（ここは著者の仕事。付録Bにそう書きます）
- **数値を本文に手打ちさせる**（必ず csv 経由で）
- **MAPIE などのライブラリを本体実装に使わせる**（検証用のみ。CLAUDE.md に明記済み）
- **差分を読まずに commit する**
